# Dynamic Source Slots Design

## Goal

Replace the single global custom-node placeholder with template-defined dynamic source slots. A template declares one or more named source slots, proxy groups reference those slots, and each Profile binds every slot to one or more existing Sources from the Sources module.

The final runtime model must not read or write the legacy `profile_sources` relation and must not accept `__WANGWANG_CUSTOM_SOURCE_NODES__`.

## Terminology

- **Source**: existing Wangwang node source from the Sources module.
- **Source Slot**: logical node-source input declared by a template.
- **Binding**: Profile-level mapping from a Source Slot to one or more Sources.
- **Slot placeholder/key**: immutable generated string such as `__WANGWANG_SOURCE_SLOT_a8f3k2__`.

## Template format

Templates declare source slots in reserved Wangwang metadata:

```yaml
x-wangwang:
  sources:
    - key: __WANGWANG_SOURCE_SLOT_a8f3k2__
      name: 主力节点
    - key: __WANGWANG_SOURCE_SLOT_p7m4x1__
      name: 游戏节点

proxy-groups:
  - name: 🚀 节点选择
    type: select
    proxies:
      - __WANGWANG_SOURCE_SLOT_a8f3k2__
      - DIRECT
  - name: 🎮 游戏节点
    type: url-test
    url: https://www.gstatic.com/generate_204
    interval: 300
    proxies:
      - __WANGWANG_SOURCE_SLOT_p7m4x1__
```

`x-wangwang` is internal template metadata and must be removed before emitting final Mihomo YAML.

## Source Slot constraints

A valid template must satisfy all of the following:

- It contains between 1 and 20 source slots.
- Each slot has a non-empty display name after trimming; maximum 40 characters.
- Slot names are unique within a template.
- Slot keys are unique within a template.
- New slot keys are generated by Wangwang; users cannot edit keys directly.
- Keys match `^__WANGWANG_SOURCE_SLOT_[A-Za-z0-9_-]{6}__$`.
- Every declared slot is referenced by at least one `proxy-groups[].proxies` entry.
- Every source-slot placeholder referenced by a proxy group is declared in `x-wangwang.sources`.
- `__WANGWANG_CUSTOM_SOURCE_NODES__` is invalid in the new runtime model.
- Unknown `__WANGWANG_*__` placeholders are invalid.

New user-created keys use `__WANGWANG_SOURCE_SLOT_${nanoid(6)}__`. Built-in templates may use stable fixed six-character suffixes.

## Visual template editor

`VisualTemplateDraft` gains `sourceSlots: SourceSlotDraft[]`, where:

```ts
type SourceSlotDraft = {
  key: string
  name: string
}
```

`ProxyGroupMemberDraft` replaces `{ kind: 'all-proxies' }` with:

```ts
{ kind: 'source-slot'; slotKey: string }
```

The visual editor adds a “节点源槽位” section before proxy groups. Users can create a slot by entering only its display name; the application generates the immutable key. The proxy-group member picker lists all slots by display name alongside groups, DIRECT, and REJECT. A group may contain multiple source slots and may mix them with other members.

Deleting a source slot is blocked while any proxy group references it. The UI must show which groups reference the slot instead of silently cascading deletion.

## Template lifecycle and structural lock

If a template has `profileCount > 0`, its slot structure is locked:

- Renaming a slot is allowed.
- Reordering slots is allowed.
- Adding a slot is forbidden.
- Deleting a slot is forbidden.
- Changing a slot key is forbidden.

The backend enforces this by comparing the old and new slot-key sets during template PATCH; the UI lock is only a convenience.

A legacy template with `migration_status = needs_repair` is the one exception: it may be structurally repaired once. After a valid new-format template is saved and all validation passes, its status becomes `ready`; normal structural locking applies from then on.

## Database model

Add:

```text
profile_source_bindings
  profile_id TEXT NOT NULL
  slot_key   TEXT NOT NULL
  source_id  TEXT NOT NULL

PRIMARY KEY(profile_id, slot_key, source_id)
FOREIGN KEY(profile_id) REFERENCES profiles(id) ON DELETE CASCADE
FOREIGN KEY(source_id)  REFERENCES sources(id) ON DELETE CASCADE
INDEX(source_id, profile_id)
```

Add to `templates`:

```text
migration_status TEXT NOT NULL
migration_error  TEXT NULL
```

`migration_status` values are `ready` and `needs_repair`. New custom templates are created as `ready`. Built-ins report `ready` from the resolver/view layer.

The old `profile_sources` table remains physically present for one release as migration/rollback data, but the new runtime must perform zero reads and zero writes against it. A later migration removes the table.

## Template API

Template summaries/details expose:

```ts
type TemplateSourceSlot = {
  key: string
  name: string
}

type TemplateMigrationStatus = 'ready' | 'needs_repair'

sourceSlots: TemplateSourceSlot[]
migrationStatus: TemplateMigrationStatus
migrationError: string | null
```

The Profile UI uses `sourceSlots` from the Template API and does not parse YAML itself.

Templates in `needs_repair` cannot be selected for new Profile creation or compiled.

## Profile API and binding rules

Replace `sourceIds: string[]` with:

```ts
type ProfileSourceBinding = {
  slotKey: string
  sourceIds: string[]
}

sourceBindings: ProfileSourceBinding[]
```

A Profile is valid for compilation only when:

- Its template is `ready`.
- Every template slot has exactly one binding entry.
- No binding references an unknown slot.
- Every binding contains at least one Source.
- Every Source exists.
- New bindings cannot add disabled Sources.
- Every slot has at least one enabled Source.
- A Profile uses at most 20 distinct Sources across all slots; the same Source bound to multiple slots counts once.

The same Source may be bound to multiple slots.

When switching templates, bindings for identical slot keys are preserved, bindings for removed keys are discarded, and new keys start empty. The Profile cannot be saved until every new slot is fully bound.

## Source lifecycle integrity

Deleting a Source is forbidden if doing so would leave any Profile slot with zero bound Sources.

Disabling a Source is forbidden if doing so would leave any Profile slot with zero enabled Sources.

Existing disabled bindings created by legacy migration may remain, but a Profile cannot recompile until each slot has at least one enabled Source. New Profile edits cannot add disabled Sources.

Source `profileCount` counts distinct Profiles, not binding rows, because one Source may be bound to multiple slots in the same Profile.

## Compilation model

Replace the global-node selection pipeline with a slot-aware selection pipeline. Fetch all bound Sources and their entries in one/few queries, preserving the existing global Profile tag-filter semantics and avoiding N+1 queries per slot.

The selection result must distinguish:

```ts
type SelectedSlotNode = {
  slotKey: string
  entryId: string
  sourceId: string
  name: string
  config: ProxyConfig
}
```

Rendering has two separate concepts:

1. **Global proxy catalog** — unique proxy definitions keyed by `entryId`.
2. **Slot membership** — ordered `slotKey -> entryId[]` membership.

The renderer first assigns final globally unique proxy names. Different entries with the same display name keep the current `name`, `name-2`, `name-3` behavior. It then maps every slot entry ID to that final proxy name.

For each proxy-group member that is a source-slot placeholder:

1. Read only that slot's proxy names.
2. Apply the group’s existing `filter` and `exclude-filter` to those names.
3. Expand the names at the placeholder position.
4. After all members are expanded, perform stable de-duplication of the final group member list.

A proxy may belong to multiple slots while appearing only once in root `proxies`.

A group may become empty after filtering; this is allowed and Mihomo’s group fallback semantics apply. Slot bindings themselves may not be empty.

Before returning final YAML, remove `x-wangwang` and reject any remaining `__WANGWANG_*__` placeholder.

## Preview

Template preview uses the same renderer contract.

Without `profileId`, create small distinct sample-node sets per source slot so users can observe slot expansion independently.

With `profileId`, use the Profile’s actual slot bindings. If the profile/template is not compile-ready, preview returns a clear validation error and does not alter the Profile’s stored configuration.

## Migration

Migration is one-time and semantic; the final runtime contains no legacy placeholder compatibility.

### Built-in templates

Update built-in YAML in code to the new metadata and fixed slot keys. Copy existing `profile_sources` rows for built-in-template Profiles into `profile_source_bindings` using those fixed keys.

### Custom templates that contain the legacy placeholder

For each legacy custom template that contains `__WANGWANG_CUSTOM_SOURCE_NODES__`:

1. Parse YAML.
2. Reject automatic conversion if conflicting `x-wangwang` metadata already exists.
3. Generate one six-character slot key for the template.
4. Add `x-wangwang.sources` with display name `默认节点源`.
5. Replace every legacy placeholder occurrence with the generated slot key.
6. Validate the transformed template with the new rules.
7. Copy each related Profile’s legacy `profile_sources` rows into `profile_source_bindings` under the generated key.
8. Save transformed YAML and set `migration_status = ready`, `migration_error = null`.

### Custom templates without the legacy placeholder

Do not guess which proxy group should receive a slot. Set:

```text
migration_status = needs_repair
migration_error = 具体失败原因
```

The user repairs the template manually.

### Failed migration continuity

Migration failure must never clear `profiles.compiled_yaml`.

Profiles attached to `needs_repair` templates continue serving their last successful `compiledYaml`. New compilation is blocked.

After the user repairs the template, affected Profiles may still lack valid slot bindings. They continue serving the old compiled configuration until the user completes all bindings and a new compilation succeeds. Compilation failure updates the error state but does not clear the old successful `compiledYaml`.

## Error codes

Use explicit API conflicts where appropriate:

- `TEMPLATE_SOURCE_SLOTS_LOCKED` — slot key set changed while template is in use.
- `TEMPLATE_MIGRATION_REQUIRED` — template is `needs_repair` and cannot compile/use normally.
- `PROFILE_SOURCE_BINDINGS_INVALID` — missing, extra, empty, disabled-only, nonexistent, or over-limit Profile bindings.
- `SOURCE_REQUIRED_BY_SLOT` — Source deletion or disabling would violate a slot invariant.

Template structural/YAML errors remain `422 TEMPLATE_INVALID`.

## Limits and preserved behavior

- Custom templates remain limited to 20.
- Profiles remain limited to 20.
- Distinct Sources per Profile remain limited to 20.
- Source slots per template are limited to 20.
- Root rendered proxies remain limited to 1000 and final YAML to 1 MiB.
- Profile tag filtering remains global and occurs before proxy-group `filter` / `exclude-filter`.
- Proxy-group filtering remains group-specific; no per-slot filter system is added.

## Test requirements

Tests must cover template slot cardinality, key/name uniqueness, undeclared/unused references, legacy placeholder rejection, YAML round-trip, slot rendering, overlapping slots, duplicate proxy names, group stable de-duplication, filters, Profile binding validation, template switching, structure locking, Source delete/disable guards, built-in migration, custom migration success/failure, disabled legacy bindings, `compiledYaml` continuity, and absence of internal metadata/placeholders in emitted Mihomo YAML.
